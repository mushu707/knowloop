# knowloop · RAG 评估方案

> 状态：S0 定稿 · 2026-11-03
> 这份文件存在的唯一目的：**防止"生成出来的题看起来像题"冒充"题目能用"。**
> S5 的出口是这张表上的数字，不是"我觉得效果还行"。

---

## 1. 为什么单独一份文档

RAG 出题是这项目唯一无法靠阅读代码判断质量的部分。Agent 能把管线写完并跑通，跑出来的东西也可能全是**看似合理、实际脱离原文**的题——而这恰恰是这个产品存在的基础（题目必须来自你的资料，否则你不如去刷现成题库）。

所以 S4（打通链路）和 S5（量化质量）必须分开。S4 的验收标准只是"代码能跑出 10 道题"，**不许把 S4 当完成**。

---

## 2. 评估语料（30 份）

### 构成

| 类别 | 份数 | 用途 |
|---|---|---|
| 结构化八股笔记（有明确小标题层级） | 12 | 主战场，验证正常情况 |
| 面经叙述体（口语、跳跃、无结构） | 8 | 验证分块策略在烂文本上的鲁棒性 |
| 官方文档摘录（MDN / React 文档等） | 6 | 长句、术语密度高、代码片段多 |
| **从网页复制的脏文本（含表格/代码块残留）** | 4 | 带导航栏残留、断行随意、中英混排——比 PDF 更接近真实输入 |

### 硬性要求

- **每份 ≥ 1500 字**，短于这个长度分不出块，测不出东西。
- **必须是你真的会去刷的内容**，不是为测试凑的。凑出来的语料会让指标虚高。
- **不许用同一份文档的复制粘贴充数**——`sha256` 去重会直接拦掉，白忙。

### 来源（按优先级）

1. 你自己的笔记 / 收藏夹 / 面试复盘（最优，有真实的使用动机）
2. 公开面经：**自己整理成条目，不下载原文二次分发**（避免版权问题）
3. 官方文档（MDN、React、TypeScript Handbook，许可证允许引用）

### 清单模板

建 `eval/corpus/manifest.json`：

```json
[
  {
    "id": "doc01",
    "file": "corpus/doc01-event-loop.md",
    "category": "structured-note",
    "chars": 3200,
    "note": "事件循环，含宏任务/微任务对照表"
  }
]
```

**S0 结束时这个文件里至少要有 10 条**。剩下 20 条可以在 S1–S4 期间陆续补——但如果 S4 结束时不满 30 条，S5 无法开始。

## 3. 金标题（100 道）

### 它是什么

不是"标准答案题库"，而是**对某段原文"应该能出什么题"的规格描述**。一条金标题长这样：

```json
{
  "id": "g007",
  "docId": "doc01",
  "allowedChunkText": "微任务队列在每个宏任务结束后清空，且在渲染之前",
  "expectedKpIds": ["kp_xxx_event-loop"],
  "requiredFacts": ["微任务在宏任务之后执行", "清空微任务发生在渲染之前"],
  "forbiddenFacts": ["微任务和宏任务同时执行"],
  "suggestedType": "single",
  "difficulty": 2
}
```

### 怎么产

**每份文档手写 3–4 条，共 100 条。** 不许多写——金标题的价值在于它是"人类认定的好题"，写多了就不金了。

写法：读完一份文档，问自己"如果明天面试官只问一个问题，问哪个最能看出我懂了"，那就是金标题。

### 判定生成题是否命中金标题

一条生成题 `G` 与金标题 `K` 匹配，需同时满足：

1. `G.kpIds` 与 `K.expectedKpIds` 有交集
2. `G` 的 correct answer 覆盖 `K.requiredFacts` 中 ≥ 80% 的要点（人工判）
3. `G` 的题干不含 `K.forbiddenFacts` 所描述的错解方向

一个金标题被 0 道生成题命中 → 记为**漏出**；被 ≥ 2 道命中 → 只计最好的一道，其余不计（防刷指标）。

## 4. 五项指标

全部在 `pnpm eval` 里自动算，只有一处需要人工标注（可用率）。

### ① 引用命中率 citationHitRate ≥ 80%

```
citations = 生成题的 source.chunkIds
hit = citations 中至少一个 chunk 的 [charStart, charEnd] 与金标题 allowedChunkText 在原文中的区间有重叠

citationHitRate = 命中题数 / 全部生成题数
```

**含义**：模型说的"出处"是不是真的出处。低于 80% 说明你的追问引用是假的，用户点回去会看到无关段落——这是最伤信任的失败模式。

### ② 题目可用率 usableRate ≥ 70%

人工逐题判，四项全过才算可用：

- [ ] 答案在原文中**有明确支撑**（能指出是哪一句）
- [ ] 题干无歧义（不存在"两个选项都对"）
- [ ] 与已有题目不重复
- [ ] 作为一道题**值得刷**（不是把原文原句挖掉一个词）

**第 4 项最重要**，也是最容易被自动化指标漏掉的。挖空题看起来合格率 100%，但毫无训练价值。

标注方式：`eval/labels/usable.csv`，列 `questionId, pass, failReason`，`failReason` 取值 `no-grounding | ambiguous | duplicate | trivial`。

### ③ 重复率 dupRate ≤ 10%

```
同 batch 内两题满足以下任一即为重复：
  a. contentHash 相同
  b. 题干 embedding 余弦相似度 > 0.92
```

### ④ 幻觉率 hallucinationRate ≤ 5%

答案涉及的事实**在检索到的 chunk 里找不到依据**的比例。与 ① 的区别：① 测"引用是否指对地方"，④ 测"答案本身是不是编的"。选题时必须开 `strictMode: true`，关闭时此项不计入验收。

### ⑤ 端到端耗时 p95

从点击"生成"到题目入库列表出现。目标 p95 < 45s（10 题，本地 embedding + 云端 chat）。超过就说明分块或并发策略有问题。

## 5. 通过标准

| 指标 | 阈值 | 不达标时先改什么 |
|---|---|---|
| citationHitRate | ≥ 80% | 检索 topK → 分块粒度 → prompt 里对引用的硬性要求 |
| usableRate | ≥ 70% | prompt 的题型约束 → 是否给了 few-shot 示例 |
| dupRate | ≤ 10% | batch 内去重 → 检索时排除已用 chunk |
| hallucinationRate | ≤ 5% | 是否真的只喂了检索结果 → 温度 → 换模型 |
| p95 耗时 | < 45s | 并发 → 流式解析 → chunk 数上限 |

**五项全过才算 S5 完成。** 有一项不过就继续调，不要"先上线再优化"——这个产品没有别的价值支点。

## 6. 跑法

```
eval/
  corpus/            30 份文档 + manifest.json
  golden/            100 条金标题 JSON
  labels/            usable.csv（人工标注）
  run.ts             pnpm eval 的入口
  reports/           eval-report.json + eval-report.md（自动生成，进 git）
```

`pnpm eval` 做四件事：

1. 对 corpus 每份文档跑完整管线（解析 → 分块 → 嵌入 → 检索 → 出题）
2. 用 golden 匹配生成题，算 ①②③④
3. 读 labels/usable.csv 算 ②（缺标注则跳过并警告）
4. 输出 `reports/eval-report.md`，五项指标 + 每个失败样本的原文引用

**同一份报告要能对比两次运行**——改完 prompt 后跑一次，看哪项动了、哪项退步了。没有这个对比，调参就是在黑暗中摸索。

## 7. 标注一致性

一个人标注会有漂移。做法：

- 间隔 7 天，随机抽 20 道题**盲标第二次**，比较两次结果。
- 一致率 < 85% 说明"可用"的定义在你脑子里还没稳定，回去收紧 §4② 的判定标准，而不是继续标。

## 8. 反模式（写在这里是为了在 S5 时有据可查）

| 反模式 | 为什么危险 |
|---|---|
| 用"看起来像题"当通过 | 这是本方案存在的全部理由 |
| 只测好文档，不测烂文档 | 真实用户的资料 80% 是烂的 |
| 指标不达标就换更大的模型 | 换模型会同时掩盖检索层和 prompt 层的问题 |
| 用真实用户文档跑 LangSmith | 违反本地优先承诺（见 `DECISIONS.md` D9） |
| 只跑一次就定论 | 单次结果方差极大，至少跑 3 次取中位数 |
| 把指标写死在代码里 | 阈值会变，放 `eval/config.json` |
