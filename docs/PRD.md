# knowloop · v0.1 产品定义

> 状态：S0 定稿 · 2026-11-03
> 本文是范围契约。任何"顺手也做了吧"的想法，先进 §6 的非目标清单，再讨论。

## 1. 一句话定位

**一个纯静态、本地优先的前端面试刷题工具：把你的面经文档变成带出处的题目，并盯住你错在哪个环节。**

三个关键词，缺一个就不是这个产品：

- **本地优先**：题目、作答记录、文档原文全部只存在于浏览器本地（IndexedDB / OPFS）。没有账号，没有服务器，没有上传。
- **RAG 出题**：题目不是从某个平台的题库里拉的，是从**你自己的资料**里生成的，且每道题能点回原文。
- **错因闭环**：记录的不是"错了哪道题"，而是"错了哪个推理环节"，并据此安排复习。

## 2. 用户

**v0.1 只服务一个人群：准备前端面试的开发者。** 就是你自己。

不是"所有考试人群"，不是"跨行业通用工具"。跨行业是 v0.2 插件层的属性，不是首发功能——**首发必须有一个你每天真的会用的场景，否则 RAG 出题质量无从验证**。

典型场景：手上攒了十几份面经 / 八股笔记 / 官方文档摘录，看第二遍就看不进去了，也不知道自己到底哪块虚。想把它们变成能刷的题，且错的时候能说清是"概念没记住"还是"两个相似概念搞混了"。

## 3. 为什么现在做

- 现有开源方案（砺知考公、OpenExam、Shiroha Quiz、QuizKit、VaultQuiz 等）已验证"本地优先 + BYO 模型 + 自定义导入"是成熟范式，不需要重新验证可行性。
- 但**它们全是桌面端或自托管脚本，没有一个是 Web 原生 + 移动可用的**；也**没有一个把"错因"当核心数据模型**，多数只有错题本。
- "开放题库分发层"在开源生态里基本是空白——这是 v0.5 的机会，不是 v0.1 的任务。

## 4. v0.1 范围

### 做

| 模块 | 边界 |
|---|---|
| 刷题 | 单选 / 多选 / 判断三种题型；手动录入 + JSON 导入 |
| 文档导入 | **粘贴正文**（主入口）+ `.md` 文件 → 分块 → 本地嵌入 → 检索 → 出题（带原文引用） |
| 错题 | 错题本、按知识点错题率、薄弱知识点排序、错因受控词表 |
| 复习 | SM-2 调度，生成"今日复习队列" |
| 模型 | BYO：OpenAI 兼容端点（DeepSeek / Qwen / Ollama / LM Studio / vLLM 均可） |
| 端 | 响应式 Web + PWA，可装到主屏，断网可刷 |
| 分发 | 纯静态托管，零后端 |

### 不做（v0.1 明确排除）

- 账号、云同步、任何形式的服务端
- 插件系统（v0.2 从核心抽出）、题库市场（v0.5）
- **PDF / Word / 图片 / 扫描件导入（v0.2 起，见 `DECISIONS.md` D11）**
- 直接抓取 URL 正文（纯前端受 CORS 限制，改为「用户粘贴正文 + 选填来源链接」，见 D12）
- 填空题、简答题、主观题、代码题
- BKT / IRT / 深度知识追踪（v0.5 起）
- 原生 App（v0.3 用 Tauri 包装同一份代码）
- 站内交易、审核工作台、付费

**为什么砍掉填空题**：填空判分需要规范化比对 + 容错，会让"错题率"这个核心指标带上歧义。主观题更糟——要对同一道题烧第二次 LLM 调用去判分，成本和延迟翻倍，且判分本身不可信。**你的核心指标只有在判分零歧义时才成立。**

## 5. 核心旅程（验收时逐条手点）

1. **上手**：打开 → 无需登录 → 看到空题库 → 粘贴一份 Markdown 面经 → 30 秒内看到 10 道带引用的题。
2. **刷**：进入练习 → 答错一道 → 立刻看到解析、原文出处、以及"你错在哪"的选项（错因）。
3. **看诊断**：进错题页 → 看到"JS 事件循环 60% 错误率"排第一 → 点进去直接刷这个知识点的错题。
4. **隔天回来**：打开就有"今日待复习 12 题"，按 SM-2 排好的。

这四条走不通，功能清单全绿也不算做完。

## 6. 成功指标

| 指标 | 目标 | 测法 |
|---|---|---|
| 你自己连续使用 | ≥ 14 天不断 | 看本地 attempts 的时间跨度 |
| 真人用户 | ≥ 5 人完成一次「导文档 → 刷完 10 题」全流程 | 屏幕共享旁观，不代劳 |
| RAG 题目可用率 | ≥ 70% | 见 `EVAL.md` |
| 引用命中率 | ≥ 80% | 见 `EVAL.md` |
| 首屏可交互 | < 2s（本地启动） | Lighthouse |

**不用 star 数、不用注册数、不用 DAU 衡量 v0.1。** 这是验证期，唯一的真问题是"生成出来的题值不值得刷"。

## 7. 交付节拍

| 切片 | 内容 | 出口 |
|---|---|---|
| S0 | 三份文档（本文件 + DATA-CONTRACT + EVAL） | 不装依赖、不写业务代码 |
| S1 | 壳：构建、存储、路由、题库列表 | 导入 JSON → 列表可见 → 点开一道题 |
| S2 | 刷题闭环 | 作答 → 判分 → 落库 → 错题本出现 |
| S3 | 错题与调度 | 知识点错题率、薄弱排序、今日队列 |
| S4 | 文档导入 + RAG 出题 | 上传面经 → 10 题 → 引用可点回原文 |
| S5 | 评估与调优 | 跑出 EVAL 五项数字 |
| S6 | PWA + 离线 + 分发 | 主屏可装、飞行模式可刷 |
| S7 | dogfood 2 周 + 5 真人 | 收 bug 清单，不加功能 |

## 8. 风险

| 风险 | 应对 |
|---|---|
| **RAG 出题质量不达标**（最大风险） | S4 与 S5 分离：先跑通链路，再用金标题量化。不许"看起来像题"就过关 |
| 冷启动没内容 | 30 份语料在 S0 就要开始攒（见 `EVAL.md` §2），不是写代码时才发现没有 |
| 错题口径被后续插件污染 | 错因用受控词表 + 尝试记录只追加不改写，见 `DATA-CONTRACT.md` §7 |
| Agent 把 schema 写歪 | schema 在 S0 冻结，S1 起 Agent 只能实现不能改形 |
| 过早抽象跨端 / 插件 | 见 §4 非目标；插件是 v0.2 从核心抽出来的，不是搭出来的 |

## 9. 命名与许可

- 仓库：`knowloop`
- 许可：AGPL-3.0（v0.1 后补 CLA）
- 已知取舍：纯前端静态分发让 AGPL 的实际约束力弱于服务端场景，长期护城河是题库与插件生态的黏性，不是协议本身。
