# knowloop · 关键决策记录（ADR）

> 2026-11-03 定稿。每条都写了**"什么条件下应该推翻我"**——这是这份文件的价值所在。
> 没写推翻条件的决策，等于信仰。

---

## D1 · 纯静态本地优先，零后端

**决定**：Vite + React SPA + PWA，数据存 IndexedDB / OPFS，无服务端、无账号。

**理由**：一个人维护、零运维成本、数据属于用户、离线可用。也让"为 SEO 上 Next.js"这个建议失去前提——用户题库在本地，本来就没有可被索引的页面。

**替代方案**：Next.js + Supabase + Python RAG（DS 原方案）；Tauri 桌面。

**推翻条件**：出现"必须多设备同步"的真实需求，且用户愿意为此注册账号。那时先加一个**可选的**同步服务，不要改成本地优先的反面。

---

## D2 · 全 TypeScript，不引入 Python

**决定**：解析、分块、嵌入、检索、调度全部 TS 实现。

**理由**：一个人维护的项目，读不懂的语言等于死代码。而 RAG 的 prompt、分块参数、检索阈值恰恰是必须反复调的地方。加上本地 Python 服务的分发成本（三平台打包、杀软误报、端口占用、启动延迟）远超它带来的解析质量提升。

**替代方案**：TS + 本地 FastAPI sidecar；TS + 云端 Python 服务。

**推翻条件**：产品必须支持复杂版式 PDF / 扫描件，且浏览器内 OCR 质量被证明不可接受。**即便如此，也应先试独立桌面版（Tauri + 嵌入式 Python），而不是给 Web 版加 sidecar。**

---

## D3 · v0.1 只服务前端面试

**决定**：不做"通用跨行业工具"，跨行业是 v0.2 插件层的属性。

**理由**：需要至少一个每天真用的场景来验证 RAG 出题质量。没有 dogfood 场景，就没有评估数据，S5 无从谈起。

**推翻条件**：无。这是范围纪律，不是技术选择。改它必须有 30 份非前端语料 + 一个新的 dogfood 用户，否则不许改。

---

## D4 · 错题不落库，从 attempts 派生

**决定**：`attempts` 只追加；错题本、错题率、薄弱排序全是纯函数推导。

**理由**：一份数据只能有一个真相源。建 `mistakes` 表必然双写，双写必然漂移，而错题率是核心指标。

**代价**：十万条 attempts 折叠会慢。解法是内存缓存 + 按 bank 分片重算。

**推翻条件**：attempts 量级到 50 万以上且重算超过 300ms。此时加**物化视图表**（可随时从 attempts 全量重建），而不是加"另一份真相"。

---

## D5 · 错因用受控词表，不用自由文本

**决定**：固定 7 个 ErrorTag。「蒙对」不在词表里——它是答对时的状态，由 `Attempt.selfConfidence === 1` 派生。

**理由**：同一个错误换个说法就统计不到一起。而"蒙对"如果也做成一个可点选的状态，就会和 `selfConfidence` 双写，出现"自评没把握却没点蒙对"的自相矛盾记录。一份数据只能有一个真相源。

> 修订记录：S1 定稿时把 `lucky_guess` 放进了词表，S2 实现时发现双写问题后删除。详见 `DATA-CONTRACT.md` §16。

**推翻条件**：插件（v0.2）可以**扩展**词表项，但不得替换核心 7 项，且扩展项必须带映射到核心项的 `mapsTo`。

---

## D6 · 题型只做单选 / 多选 / 判断

**决定**：不做填空、简答、主观、代码题。

**理由**：核心指标只有在判分零歧义时才可信。主观题需要对同一道题烧第二次 LLM 调用，且判分本身不可信。

**推翻条件**：v0.3 之后，且已有一个可量化的"判分与人工一致率 ≥ 95%"的 LLM 判分器。

---

## D7 · Embedding 本地跑，Chat 走 BYO

**决定**：`bge-small-zh-v1.5`（int8，~25MB）本地嵌入；出题用用户自己的 OpenAI 兼容端点。

**理由**：用户全程只需填一个 key，本地优先的叙事才闭环。双 key 会让 90% 的人在导入文档那一步流失。

**代价**：首次进 RAG 页要下模型，需进度条；本地嵌入慢于服务端 GPU（单用户可接受）。

**推翻条件**：本地嵌入在低端移动设备上被证明不可用（>30s/千 chunk）。

---

## D8 · 不上 LangChain / LangGraph 进运行时

**决定**：`src/` 里零 LangChain。流水线自己写（约 400 行）。`experiments/` 里随便用。

**理由**：LangChain 解决的是"编排不用管细节"，而这项目的全部难点就在细节（分块、topK、prompt 结构、引用强约束）。中间隔一层框架，你调试的是框架内核而不是你的问题。LangGraph 的 durable execution 在无服务端场景无处落地（checkpointer 只能自己塞 IndexedDB）。

**注意**：LangSmith 是云服务，**不许用来跑真实用户文档**（违反 D1）。只能用 `eval/corpus` 的自有语料。

**推翻条件**（三条同时成立才考虑）：
1. 出现有环、需要中断续跑的工作流（例如 v0.3 的"AI 学习教练"）
2. 该工作流的状态机复杂度超过 5 个节点
3. 你已经能自己写清楚这套状态机（先手写一版，再决定要不要框架）

---

## D9 · 自定义模型的抽象层只有 100 行

**决定**：`ModelProvider` 接口 + 两个实现（openai-compatible / ollama）。embedding 不做抽象。

**理由**：2026 年 OpenAI 兼容协议已是事实标准，一个 fetch 覆盖 95% 目标用户。抽象只在有 ≥2 个实现时才值钱——embedding 只有本地一个实现，所以不给它接口。

**推翻条件**：要接 Anthropic / Gemini 原生 API（协议差异大到兼容层包不住）时，加一个实现类，不改接口。

---

## D10 · 插件是 v0.2 从核心"抽"出来的，不是搭出来的

**决定**：v0.1 只留两处插槽——`Question.extensions` 字段、`ModelProvider` 接口。插件运行时（Worker + RPC + manifest）在 v0.2 实现。

**理由**：边界不是设计出来的，是撞出来的。在你只有一种题型、一个行业、一个用户的时候设计插件契约，设计出来的一定是错的。

**安全前提（v0.2 必须遵守）**：插件只在 Web Worker 内运行，通过 RPC 访问受限 API；拿不到 DOM、拿不到 IndexedDB 直连、拿不到用户文档原文。

**推翻条件**：出现第二个**真实**用户要求"我要把我的行业的判题规则接进来"。到那时边界自然浮现。

---

## D11 · v0.1 不支持 PDF

**决定**：输入只有 `text/plain`（粘贴）和 `text/markdown`（上传 .md）。`Document.mime` 收窄为这两个值。

**理由**：目标用户的材料全是「收藏的网址、纯文本、Markdown」，没有一份 PDF。而 PDF 解析要吃 1–2 天，还要处理排版错乱、表格拍平、扫描件无文字层一整类边界。为一个没有证据的需求付这个成本不值得。

**代价**：`EVAL.md` 里原本的「含表格 PDF ×4」语料改成「从网页复制的脏文本 ×4」——对分块的考验更狠，也更接近真实输入。

**推翻条件**：真实用户（不是假想用户）明确因为不支持 PDF 而弃用，且人数 > 3。

---

## D12 · 粘贴正文是第一等输入，不做 URL 抓取

**决定**：v0.1 的主入口是「粘贴一段正文 + 可选填来源 URL」，`Document.sourceUrl` 只存字符串。

**理由**：纯前端 `fetch` 任意站点会被 CORS 挡死，"输入一个网址自动出题"在无后端前提下不存在。而用户的实际动作本来就是「打开文章 → 选中 → 复制」，所以粘贴才是正确的原语，不是妥协。存 URL 是为了保住"从题回到原文"的回链，但**绝不去抓它**。

**推翻条件**：有了可选后端，且用户明确要求书签式的一键导入。那时是新增一条输入路径，不是替换粘贴。

---

## D13 · 判分二值，不引入部分得分

**决定**：`GradeResult.correct` 是 boolean。多选采用集合完全相等：少选、多选、错选都为错。

**理由**：`kpWrongRate` 的分母是作答次数，一旦引入"半对"，每个页面都要回答"半对算不算错"——两种答案都有道理，于是每个页面算出不同结果。多选的"部分正确"有价值，但它是**展示层**的信息（UI 上列出"你选了 a、c，正确答案是 a、c、d"），不该成为统计口径。

**推翻条件**：出现"必须按得分率评估"的需求（比如考试模式）。那时加 `score` 字段作为**新增**维度，`correct` 保留且语义不变。
